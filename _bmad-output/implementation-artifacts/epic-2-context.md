# Epic 2 Context: See an explained Match score

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

The Student submits a CV and a Job ad and sees «71 % samsvar – 5 av 7 nøkkelord» with its formula and Verdict, the CV line behind every Matched keyword and the ad line behind every Missing one. Ordinary code produces all of it, with no AI. «Bruk eksempelet» fills in the Example pair. Fixtures with hand-written Answer keys prove the score is right, and on 17 Nov the FR-5b decision is taken: can code alone extract Keywords well enough, or may AI propose the list?

## Stories

- Story 2.1: Write the Example pair Fixture (frontend, English terms)
- Story 2.2: Write the nursing Fixture (outside IT, «sårvurdering»)
- Story 2.3: Write the two-column Fixture (split compounds, «prosjektledelse»)
- Story 2.4: Normalise and stem Norwegian words
- Story 2.5: Extract Keywords from the job ad with a versioned vocabulary
- Story 2.6: Find each Keyword in the CV text, with its Evidence
- Story 2.7: Score the inputs on the server (phase 1)
- Story 2.8: Read the score and the keyword lists on Søknad
- Story 2.9: See the job ad drawn as a pulse plot
- Story 2.10: Try the app with the example
- Story 2.11: Decide whether code alone extracts Keywords well enough (FR-5b)

## Requirements & Constraints

- Keywords are skills, tools, technologies, methods, qualifications and domain terms named in the ad, from any field (not only IT), including English terms common in Norwegian ads («Agile», «stakeholder»). Stop words and boilerplate are not Keywords; duplicates and inflected forms count once.
- Match score = Matched ÷ all Keywords × 100, rounded to a whole number; equal weight per Keyword. Verdict is Strong match («Sterkt samsvar») at 70 or above, Needs work («Bør forbedres») below, judged on the rounded score. The UI shows «X av Y nøkkelord» and a one-line formula.
- Same inputs always give the same Keyword list and score (NFR-6); the Fixtures are run twice to prove it.
- Fixtures: at least 3 fictional Norwegian ones, the Example pair among them. Between them they cover: a two-column PDF CV, English technical terms, inflection and split compounds, a field outside IT, and the «prosjektledelse» vs semester group project case. The repository holds only fictional CVs.
- Each Answer key (the *fasit*) gives: expected Matched and Missing Keywords, the expected score (follows exactly from the two lists, no tolerance), must-not-match terms, expected Rewordable and Real gaps, and must-never-suggest items. SM-2: on every Fixture the Matched and Missing lists equal the Answer key exactly.
- Helene writes every Answer key by hand. AI may draft a CV or an ad, never the fasit, and the session log says so.
- Looser matching that raises scores makes the product less honest: only the Answer keys may justify a matching change.
- FR-5b is pending: it applies only if code-only extraction fails SM-2 on every Fixture, including a held-out one written after the vocabulary is tuned (Story 2.11).

## Technical Decisions

- Fixture folder: `data/fixtures/<id>/` with `cv.txt`, `cv.pdf` (where one exists), `ad.txt`, `meta.json` (job title, employer) and `answer-key.json`; `cached/` comes in later epics. `data/fixtures/_planted/` is for bad outputs only tests read. `cv.txt` is generated by script from the unpdf extraction of `cv.pdf` so the two never drift.
- The Answer-key zod schema lives in `src/shared/core/answer-key.ts` (shared: keywords, gaps and QA code all read it). A Vitest test parses every `answer-key.json`.
- Runtime reads of `data/` go only through `shared/server/data-files.ts`. Tests may read the files directly.
- `keywords/core` is the only judge of "the same word": one normalise/stem pipeline (case, æøå, hyphens/spaces, a small suffix pre-step for utvikler/utviklere/utviklerne, then Snowball Norwegian), compound and alias rules, `extractKeywords(adText, vocabulary)` and `findKeyword(text, keyword)`. Synchronous and pure; imports only `shared/core`. The vocabulary is versioned JSON in `data/vocabulary/` and is tuned against the Answer keys.
- Each Keyword carries its match stage (`exact` | `inflection` | `compound` | `alias`) and its positions in the ad.
- `shared/core/canon.ts` is the existing canonical-text helper (NFC, whitespace collapsed, trimmed). Lookup keys for Cached responses hash canon text of `cv.txt` and of `extract(cv.pdf)`; a test asserts that `cv.pdf`, `cv.txt` and «Bruk eksempelet» give the same key.
- `core/` is pure: no I/O, env, clock or randomness. Scripts are TypeScript run with `tsx --conditions=react-server`.

## UX & Interaction Patterns

- All UI text in bokmål from `src/shared/ui/messages.nb.ts`; WCAG 2.2 AA, single column at 360 px.
- Results show the score, the formula, the Verdict, the CV line behind every Matched keyword and the ad line behind every Missing one. «Bruk eksempelet» fills in the Example pair with or without login. The job ad is drawn as a pulse plot (Story 2.9).

## Cross-Story Dependencies

- Fixtures (2.1–2.3) come first; they and their Answer keys are the test input for the engine stories 2.4–2.6, which feed scoring (2.7) and the UI (2.8–2.10).
- 2.2 and 2.3 reuse the Answer-key schema from 2.1; 2.3 reuses `extract-fixture-cv.ts`.
- 2.11 needs a held-out Fixture written after the vocabulary is tuned, and depends on 2.1–2.7.
- Epic 3 builds Cached responses on these Fixtures; Epic 5 reads the Answer keys' gap and must-never-suggest lists.
